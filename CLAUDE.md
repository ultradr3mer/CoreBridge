# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CoreBridge is a Windows-hosted .NET 10 tool that drives **Canonical Multipass** to create and manage Ubuntu VMs, plus "Classic image profiles" that provision guests (Claude Code, .NET SDK, snaps) via generated cloud-init. Code comments, XML docs, CLI help texts and user-facing messages are written in **German** — keep that convention.

## Commands

SDK is pinned in `global.json` (10.0.401, latestPatch). Solution file is `CoreBridge.slnx`.

```powershell
dotnet build CoreBridge.slnx
dotnet test test/CoreBridge.Core.Tests                               # unit tests, no Multipass needed (mostly)
dotnet test test/CoreBridge.Core.Tests --filter "FullyQualifiedName~InitTests"    # single class
dotnet test test/CoreBridge.Core.Tests --filter "FullyQualifiedName~InitTests.SomeMethod"
dotnet test test/CoreBridge.Cli.Tests                                # full VM lifecycle (Category=Integration), needs Multipass
dotnet test --filter "Category!=Integration"                         # fast run: skips the Cli.Tests lifecycle
dotnet run --project src/CoreBridge.Cli -- vm-list                   # run a CLI verb
dotnet run --project src/CoreBridge.Tui                              # TUI app
.\scripts\ai-ubuntu.ps1 [-Part 1|2] [-Sim]                           # real setup: bare ai-ubuntu + snapshot base + clones ai-ubuntu-dotnet/-python (part 1), vm-install dotnet/python + snapshots + diagnostics (part 2), timed
.\scripts\cb-suite.ps1 [-Edge] [-Pause] [-From clone] [-Only a,b] [-List]   # user flow step by step via cb-sim (simulator); -Edge = edge cases (timeouts, trash, conflicts, bad input; VMs cbx-edge-*); -Real = real Multipass
```

Building `CoreBridge.Cli` runs an MSBuild target that executes `scripts/install-cb.ps1`, which (idempotently, between `# >>> CoreBridge cb >>>` markers) installs the `cb` and `cb-sim` functions from `scripts/cb.ps1` into the user's PowerShell profiles. `cb` wraps `dotnet run --project <root>\src\CoreBridge.Cli`, where `<root>` is found by walking up from the current directory to `CoreBridge.slnx` (so it runs whichever checkout/worktree you stand in, from any subfolder; outside a checkout it errors; without arguments it starts the TUI) and re-joins PowerShell arrays with commas (`-c claude,dotnet` would otherwise reach the parser as `-c claude dotnet` and silently drop `dotnet`). `cb-sim` is `cb` with `DOTNET_ENVIRONMENT=Simulation` for that one call (see Simulation below).

The target (`InstallCbProfileFunction`, `AfterTargets="Build"`, `IgnoreExitCode="true"`) runs on every CLI build — also via `dotnet test` of `CoreBridge.Cli.Tests` — in whichever checkout/worktree is built, and rewrites the block in both `Documents\PowerShell` and `Documents\WindowsPowerShell` profiles: the last build wins, so building an older worktree reinstalls its older `cb`. A failed install does not fail the build. Open shells keep the old function until `. $PROFILE`. To test a `cb.ps1` change without building: `pwsh -NoProfile -File scripts\install-cb.ps1`, then `pwsh -NoLogo -Command ". '<profile path>'; cb …"` from the directory under test (e.g. a subfolder, or outside any checkout).

CLI verbs (CommandLineParser): `multipass-status|restart` (restart asks to relaunch itself elevated via UAC; if the stop hangs it asks y/n before killing the service's `multipassd` PID; prompts go through `EventFactory`-interaction events, answered by the `ConsoleAdapter`, which defaults to "no"), `vm-list|create|start|stop|delete|exec|connect|put|get` (every VM verb first looks the VM up via `vm-list` and reports missing/trashed VMs with a ready message: `vm-create` asks before replacing an existing VM of the same name (stop + `delete --purge`), `vm-start`/`vm-stop` are no-ops when already running/stopped, `vm-delete` asks before deleting a running VM, `vm-exec|connect|put|get` offer to start a stopped VM; start/stop/delete ask "keep waiting?" after each `DefaultTimeout`; `vm-create` waits in slices of `DefaultTimeoutVmCreation` and asks "keep waiting?" after each; on "no" the daemon keeps launching in the background and a `TextEvent` reads a follow-up command that is parsed and dispatched like normal CLI args), `vm-clone|snapshot|snapshots|restore` (Multipass only clones/snapshots/restores **stopped** VMs: a running one is stopped after asking; `vm-clone` waits in `DefaultTimeoutVmCreation` slices because it copies the disk, and on "no" Multipass finishes the clone in the background; the clone carries everything cloud-init installed in the source, so a provisioned base VM + clones skips re-provisioning; `vm-restore` always passes `--destructive` (without it Multipass prompts on a redirected stdout and hangs) and first takes a backup snapshot unless the user explicitly discards the current state, so without a console it always backs up), `vm-install -n <vm> -c dotnet,python [--snapshot <name>]` (installs components into an existing VM with the same steps cloud-init runs at create: wait for cloud-init, `apt-get update`/packages, snaps, upload the component script LF-normalized to `/tmp`, `install` it to its `InstallPath`, run it as `InstallUser`, then require its `/var/lib/corebridge/<c>.ready` marker; plan in `Inits/InitInstall.cs`; starts a stopped VM without asking; the first failing step ends the command naming the step and leaves the VM running for diagnosis), `vm-resize -n <vm> -d 20G` (relays `multipass set local.<vm>.disk=<size>`; Multipass only modifies **stopped** VMs and only grows disks, so shrinking and invalid sizes are rejected via `MultipassSize` *before* a running VM gets stopped (after asking); a VM that was running is started again, and cloud-init `growpart` grows the guest root partition on boot; idea: keep base VMs/snapshots small, grow a clone when work starts), `repo-send -n <vm> [-r <path>]` / `repo-receive -n <vm> [-i <id>] [--diff] [--yes]` (task cycle, step 1 — Claude's work in the VM goes back to the host repo; names deliberately avoid git's own verbs (push/pull/fetch); no SSH: commits travel as `git bundle` files via `multipass transfer` + `multipass exec`, because `multipass exec` on Windows forwards no stdin, so git's live pack protocol can't run over it; send: requires the git component (`git.ready` marker + git, fail closed), bare repo `~/repos/<repo>.git`, bundles `main` with full history the first time and only `main ^<vm-main>` afterwards (fast-forward only, like a push without `--force`), workspace `~/work/<repo>` (clone, or only fetch — reset belongs to the future task start); repo name comes from the common `.git`, so a worktree sends as its main repo; receive without `-i` lists `claude/*` branches of the bare repo, with `-i` it requires `main` checked out and clean, bundles `claude/<id>` in the VM (excluding the VM's `main` if the host has it), fetches it to `refs/remotes/<vm>/claude/<id>`, shows log + diffstat and, only after yes/`--yes`, fast-forwards main (`merge --ff-only`, commit ids stay those from the VM); if main has commits the task branch lacks, nothing changes (exit 1) — send main again and rebase the task in the VM. `multipass transfer` VM→host exits 2 on Windows with "cannot set permissions for local file" although the file is complete — only that exact message is tolerated. Both verbs refuse under `cb-sim`. Still to come: Stop hook `claude-checkpoint`, task lock/start, scanning), `init-configure|list|delete`. **Snapshot after configuration** is standard: after a successful `vm-install` or a `vm-create` with profile/cloud-init the CLI recommends a snapshot ("stable state before anyone connects"), asks yes/no (no console → no), or takes it without asking with `--snapshot <name>`; the VM is stopped for it and stays stopped. After a failure there is no offer. Typical flow: `cb init-configure -n dev -c claude,dotnet` → `cb vm-create -n myvm -i dev`.

## Architecture

- **CoreBridge.Core** — all logic; no console I/O.
  - `Multipass/` (namespace `CoreBridge.Core.Multipass`): `IMultipassCli` is the seam; `MultipassCli` spawns `multipass.exe` and returns `MultipassRunResult` (exit code, stdout, stderr, duration); it is `virtual`/injectable for tests — `Run` waits once, `RunWithExtensions` waits in slices and asks a `keepWaiting` callback. `MultipassBinaryLocator` resolves the binary: env `CORE_BRIDGE_MULTIPASS_EXE` → `PATH` → `%ProgramFiles%\Multipass\bin\multipass.exe`. `MultipassService` backs `multipass-restart` (controls the Windows service via `sc` output parsing); its waits stream `Progress.ProgressTick` (`.`) lines, turned into `ProgressEvent`s, and throw `MultipassServiceTimeoutException`. Long VM verbs (create/start/stop/delete/clone/snapshot/restore/exec/put/get) run through `Program.WithProgress`, which emits a `ProgressEvent` every 200 ms while no interaction is open; `ConsoleAdapter` draws them as an in-place spinner `- / | \` with the seconds waited, or as dots when stdout is redirected (no carriage-return garbage in logs). When the user answers "keep waiting?" with no, create/clone report that Multipass continues in the background (exit 0); start/stop/delete say the same but exit 1, because a following step (delete after stop, exec after start) must not build on an unfinished state. `SimulatedMultipassCli` (free play-through) and `ReplayMultipassCli` (exact replay) are the stand-ins for development without Multipass (see below).
  - `Vm/`: `VmService` wraps the verbs. `Doctor.Check` backs `multipass-status`. `VmSession` is the abstract scripted-session base (`SendLine`/`WaitFor`) with `VmConsoleSession` (arbitrary process, test hook), `VmExecSession` (each command is its own `multipass exec … /bin/sh -c`, the reliable path on Windows; the working directory carries over between commands via a `pwd` marker line, env/shell variables don't) — all three live in `VmConsoleSession.cs`. `VmService.OpenConsole` is vm-connect in programmable form (used by the lifecycle connect stage); there is no SSH anywhere in CoreBridge.
  - `Inits/` (namespace `CoreBridge.Core.Inits`): `InitService.Configure` renders cloud-init from `Images:Components` and writes `<name>.profile.json` + `cloud-init.yaml` into the `InitStore`. **It downloads nothing and manages no image** — a profile is purely generated cloud-init plus the Multipass catalog name to launch. `InitCloudInit` renders the cloud-init YAML from `Images:Components` (packages, users, snaps, and component shell scripts from `scripts/components/*.sh` embedded as files and run **in the guest only** — the host never executes them; each script takes the install user as `$1`, checks its own postconditions and touches `/var/lib/corebridge/<component>.ready`; shipped: `claude`, `dotnet`, `python` (3.14 from the archive, else via uv), `cline` (npm, Node ≥ 20 via NodeSource if needed), `git` (only git; needed by `repo-send`/`repo-receive`, which run git inside the VM via exec — no sshd, no keys), plus snap-only `opencode`; `ComponentScriptTests` renders them from the real `appsettings.json`); `CloudInitYamlValidator` checks it. `InitProfileResolver` decides whether a `vm-create --image` value is a CoreBridge profile (only if a profile file exists in the store) or a plain Multipass catalog name, and maps profiles to their runtime image (default `daily:26.10`) + cloud-init. `--image` stays a union type: catalog image *or* profile name.
  - `Git/` (namespace `CoreBridge.Core.Git`): `GitCli` runs git on the host (`virtual`, `GitException` for start failures/timeouts, translated in `Program.ToExecutionException`), `SandboxRepo` holds the pure pieces (VM paths, bundle paths, id rules, VM shell lines, ref parsing). `Common/Shell.Quote` is the shared quoting for guest shell lines.
  - `InitStore` is static state: `Initialize(StoreRoot)` once at startup. **Path resolution lives in `Common/RepoPaths.cs`** — `Root()` finds the directory holding `CoreBridge.slnx` by walking up from the DLL, `Resolve()` anchors relative paths there. That is the *only* place a configured path gets resolved; `Images:StoreRoot` is the relative `artifacts` in the Development default, so a private copy of this logic per caller makes files land in different places depending on the working directory. Default is `<repo>/artifacts` (gitignored). Layout: `profiles/<name>/<name>.profile.json|cloud-init.yaml`. `SchemaVersion` is 4 and the resolver rejects anything below 4 (profiles from the pre-4 model era must be re-created) — treat a bump as breaking for existing profiles.
  - **Logging & replay (no env vars)** — `CoreBridgeContainer.Create(config)` (`Common/`) builds an MS DI container (`Microsoft.Extensions.DependencyInjection`, `ValidateOnBuild`) from `AppConfig.Bootstrap` (interface FullName → implementation FullName, default `IMultipassCli → MultipassCli`; `AppConfig` is registered as an instance, so implementations may take it in their ctor; MS DI picks the ctor with the most resolvable parameters, so give an implementation exactly one public ctor — `ReplayMultipassCli.FromEntries` exists for that reason). `MultipassCliFactory.Create(services)` resolves `IMultipassCli` and, if `MultipassLogPath` is set, wraps it in `LoggingMultipassCli`, which writes each call (args, exit code, stdout/stderr, `timedOut`) as JSON Lines to `<MultipassLogPath>/<yyyyMMdd-HHmmss>-<pid>.jsonl` (resolved via `RepoPaths`). Mapping `IMultipassCli` to `ReplayMultipassCli` replays those logs instead of calling Multipass: exact args match, identical calls answered in recorded order (the last one repeats), an unrecorded call throws `MultipassException`, a recorded timeout rethrows; it is never wrapped in logging and does not call `keepWaiting`. It reproduces no host side effects (e.g. the local file from `transfer`) and installs nothing in a guest; use it for exact regression replays, not for exploring.
  - **Simulation** — `SimulatedMultipassCli` lives in the test-side library `test/CoreBridge.Simulation` (namespace `CoreBridge.Simulation`), not in Core; `CoreBridge.Cli` references it **only in Debug** so `cb-sim` can load it via the assembly-qualified `Bootstrap` entry in `src/CoreBridge.Cli/appsettings.Simulation.json` (`"CoreBridge.Simulation.SimulatedMultipassCli, CoreBridge.Simulation"`); a Release build has no simulator. It keeps VMs, snapshots and transferred files as state in `<StoreRoot>/multipass-sim/state.json` (cross-process mutex; reset by deleting the folder) and accepts any names/orders. Long verbs (launch/start/stop/restart/clone) take `MultipassSimulationDelay` (default `4s`) in slices like `MultipassCli`, so "keep waiting?" and background completion (state already changed, like the real daemon) can be played through with a small `-t`. Cloud-init is assumed successful: components found in the launch cloud-init (`corebridge-install-<name>`) answer their probes (`--version`, `.ready` markers) and travel with clones/snapshots. Output, error texts, clone/snapshot naming (`<src>-cloneN` counting named clones too, `snapshotN`, parent = last taken/restored) and list order (active VMs alphabetically, then trash) follow real recordings in `test/CoreBridge.Core.Tests/Recordings/multipass-1.16.3/`; `SimulatedMultipassCliTests.SimulatorEntsprichtDerEchtenAufnahme` replays them against the simulator. Re-record with `MultipassLogPath` pointing there when Multipass changes. Both doubles implement `IMultipassDouble`: never logged, `multipass-status` shows their pseudo path, and every VM command starts with a `[simulation://multipass] kein echtes Multipass` stderr notice. Logging is off by default; to mock locally put `"MultipassLogPath": "artifacts/mp-log", "Bootstrap": { "CoreBridge.Core.Multipass.IMultipassCli": "CoreBridge.Core.Multipass.ReplayMultipassCli" }` in `appsettings.local.json`. `multipass-restart` always stays real.
- **CoreBridge.Cli** — `Program.RegisteredOptionTypes` is the single list of verbs; `Program.Run(config, options, ct)` is the one public dispatcher (internally `Dispatch(CommandContext, IOptions)`, where `CommandContext` bundles config, `VmService`, `EventFactory` and token) and returns `IAsyncEnumerable<CliEvent>` streamed as they are produced. Every expected failure leaves `Program.Run` as a single `ProgramExecutionException` whose message is ready to display and which carries the exit code: `Program.ToExecutionException` is the one place that translates `MultipassException`, JSON and I/O exceptions and cancellation (Ctrl+C → 130). `Main` only prints it; anything else is a bug and propagates. To add a verb: add an `[Verb]` options class implementing `IOptions` in `Options.cs`, register it in `RegisteredOptionTypes`, and add a case to `Dispatch`.
  - **Menü statt Reflection** — `CommandMenu.cs` describes every verb as data: `CommandMenu(Name, Help, IReadOnlyList<CommandParameter>)` with `CommandParameter(Name, Abbreviation, Required, Help)`, and `CommandMenus.All` / `CommandMenus.ByName` (OrdinalIgnoreCase) / `CommandMenus.Find` hold all of them in the order of `RegisteredOptionTypes`. Each options class declares its own `public static CommandMenu Menu { get; }` (helpers `CommandMenu.Simple` for verbs without parameters, `CommandMenu.WithTimeout(...)` to append the inherited `-t/--timeout`, `CommandParameter.Short/Long`); `CommandMenus.All` reads those members directly, **no reflection** — so a missing verb is a compile error, and the list itself is the contract. The `Menu` member is deliberately *not* a `static abstract` member of `IOptions`: static members are not inherited, so the abstract `MultipassOptions` would have to redeclare it, and every concrete verb carries its own menu anyway. Hidden options (`pause-on-exit`) stay out of the menus. `CommandMenuTests` (the only place reflection is allowed) verifies via the `[Verb]`/`[Option]` attributes that every registered verb has a menu and that name, help, parameters, abbreviations and `Required` match.
- **Ereignisstrom der CLI** — `Program.Run` legt einen `Channel<CliEvent>` an, startet den Kommando-Task (`ProduceAsync`) und liefert `channel.Reader.ReadAllAsync()`. `EventFactory` (Feld von `CommandContext`, je Aufruf eine Instanz mit eigenem `Stopwatch`) erzeugt alle Ereignisse und versieht sie mit dem Zeitstempel: `Std`/`Err`/`Tick` sowie `Choice<T>`/`Text`, die offene Rückfragen in `IOpenInteraction`-Set bucht. `ConsoleAdapter` ist der Konsument: er schreibt Std/Err/Tick und beantwortet Rückfragen per `TryParseChoice`. Reihenfolge im `switch` zählt, weil `InteractionEvent` von `StdEvent` erbt. Rückfragen entstehen über `context.ConfirmAsync`/`PromptAsync` (warten) bzw. `EventFactory.Ask` (**blockiert**, für die `Func<bool>`-Callbacks aus Core, die auf Threadpool-Threads laufen und nicht `await`en können — deshalb der Kanal statt eines reinen Async-Iterators). Ohne interaktive Eingabe (`ConsoleAvailability.CanPrompt`, zusätzlich zu `Console.IsInputRedirected`, weil `ReadLine` ohne Konsolenfenster sonst endlos blockiert) gewinnt immer `DefaultAnswer` = `No`/`Cancel`/`null` — **nicht** `default(T)`, denn der erste Aufzählungswert ist hier der affirmative. `ProduceAsync` ruft am Ende `AssertNoOpenInteractions` auf: eine nie beantwortete Rückfrage ist ein Fehler, kein Hänger.
- **Config** (`AppConfig`, shared by CLI and TUI): `appsettings.json` → `appsettings.{DOTNET_ENVIRONMENT}.json` (defaults to `Development`, which sets `StoreRoot=artifacts`) → `appsettings.local.json` (gitignored) → env vars (`Images__StoreRoot`). Timeouts are top-level strings `DefaultTimeout` (restart / `sc`, vm-list/start/stop/delete/exec/put/get) and `DefaultTimeoutVmCreation`, parsed by `StringExtensions.ReadTime` (`10s`, `1000ms` only). Verbs deriving from `MultipassOptions` (`Options.cs`) take `-t/--timeout`, whose getter is private: only `Program.ApplyTimeoutOverride` (called from `Run` and for vm-create's follow-up command) reads it via `ITimeoutOverride` and replaces both config values for that call. Everything else reads only the config. `MultipassLogPath` (off when empty) and `Bootstrap` choose logging/replay (see above). No secrets in config; passwords come only from the `CORE_BRIDGE_[ALL|<NAME>]_PASSWORD` env chain.
- **CoreBridge.Tui** — Terminal.Gui **v2** scaffold (currently a template, not yet wired to Core). v2 is a full rewrite and v1-style code will not compile: read `src/CoreBridge.Tui/AGENTS.md` before touching UI code. Use the instance lifecycle `Application.Create().Run<T>().Dispose()`, not static `Init/Run/Shutdown`.

## Tests

- **CoreBridge.Core.Tests** — xUnit unit tests; Multipass calls are faked via `MultipassCli` subclasses / locator parameters.
- **CoreBridge.Cli.Tests** — one ordered integration lifecycle (`CliLifecycleTests`, `[Trait("Category","Integration")]`): methods are named `Stage00_…`, `Stage01_…`, `Stage05b_…` and sorted ordinally by `LifecycleTestCaseOrderer`; each stage depends on the previous one via the shared `CliLifecycleFixture`. It calls `Program.Run` in-process (no child CLI process), uses a temp `StoreRoot`, records every real Multipass call to `artifacts/mp-log/cli-lifecycle/` via `MultipassLogPath` (Bootstrap stays default, so it is always real Multipass), creates a real profile + VM named `cbx-cli-*`, and skips itself when Multipass is unavailable. Run the whole class, not individual stages.
- VMs created by tests use the `cbx-` prefix; `scripts/group-vms.ps1` groups them into a Hyper-V VM group (`-Remove` to undo).

The exploratory Multipass experiments (`test/Multipass.Experiments`) were removed on 2026-09-26; they were scaffolding for discovering Multipass behaviour, and an unfiltered `dotnet test` on the solution now only runs the two test projects above. The `Category!=Integration` filter is therefore only needed to skip the `CoreBridge.Cli.Tests` lifecycle.
