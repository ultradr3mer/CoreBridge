# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CoreBridge is a Windows-hosted .NET 10 tool that drives **Canonical Multipass** to create and manage Ubuntu VMs, plus "Classic image profiles" that provision guests (Claude Code, .NET SDK, snaps) via generated cloud-init. Code comments, XML docs, CLI help texts and user-facing messages are written in **German** — keep that convention.

## Commands

SDK is pinned in `global.json` (10.0.401, latestPatch). Solution file is `CoreBridge.slnx`.

```powershell
dotnet build CoreBridge.slnx
dotnet test test/CoreBridge.Core.Tests                               # unit tests, no Multipass needed (mostly)
dotnet test test/CoreBridge.Core.Tests --filter "FullyQualifiedName~InitTests"    # single class
dotnet test test/CoreBridge.Core.Tests --filter "FullyQualifiedName~InitTests.SomeMethod"
dotnet test test/CoreBridge.Cli.Tests                                # full VM lifecycle (Category=Integration), needs Multipass
dotnet test --filter "Category!=Integration"                         # fast run: skips the Cli.Tests lifecycle
dotnet run --project src/CoreBridge.Cli -- vm-list                   # run a CLI verb
dotnet run --project src/CoreBridge.Tui                              # TUI app
dotnet run --project tools/CoreBridge.Interaction.Demo               # plays through output, spinner, prompts and a tick offer (k/Esc) in a real console
dotnet run --project tools/CoreBridge.MultipassSim -- list           # multipass-sim.exe: the simulator with multipass.exe's command line (launch, exec, shell, list …); state shared with cb-sim
```

Never run a bare `dotnet test` on the solution to "check everything": it includes the Integration lifecycle, which creates real VMs (and may raise UAC). Use `--filter "Category!=Integration"` unless real Multipass is intended.

```powershell
.\scripts\ai-ubuntu.ps1 [-Part 1|2] [-Sim]                           # real setup: bare ai-ubuntu + snapshot base + clones ai-ubuntu-dotnet/-python (part 1), vm-install dotnet/python + snapshots + diagnostics (part 2), timed
.\scripts\cb-suite.ps1 [-Edge] [-Pause] [-From clone] [-Only a,b] [-List]   # user flow step by step via cb-sim (simulator); -Edge = edge cases (timeouts, trash, conflicts, bad input; VMs cbx-edge-*); -Real = real Multipass
```

Building `CoreBridge.Cli` runs an MSBuild target that executes `scripts/install-cb.ps1`, which (idempotently, between `# >>> CoreBridge cb >>>` markers) installs the `cb` and `cb-sim` functions from `scripts/cb.ps1` into the user's PowerShell profiles. `cb` wraps `dotnet run --project <root>\src\CoreBridge.Cli`, where `<root>` is found by walking up from the current directory to `CoreBridge.slnx` (so it runs whichever checkout/worktree you stand in, from any subfolder; outside a checkout it errors; without arguments it starts the TUI) and re-joins PowerShell arrays with commas (`-c claude,dotnet` would otherwise reach the parser as `-c claude dotnet` and silently drop `dotnet`). `cb-sim` is `cb` with `DOTNET_ENVIRONMENT=Simulation` for that one call (see Simulation below).

The target (`InstallCbProfileFunction`, `AfterTargets="Build"`, `IgnoreExitCode="true"`) runs on every CLI build — also via `dotnet test` of `CoreBridge.Cli.Tests` — in whichever checkout/worktree is built, and rewrites the block in both `Documents\PowerShell` and `Documents\WindowsPowerShell` profiles: the last build wins, so building an older worktree reinstalls its older `cb`. A failed install does not fail the build. Open shells keep the old function until `. $PROFILE`. To test a `cb.ps1` change without building: `pwsh -NoProfile -File scripts\install-cb.ps1`, then `pwsh -NoLogo -Command ". '<profile path>'; cb …"` from the directory under test (e.g. a subfolder, or outside any checkout).

`artifacts/` (profile store, simulator state, local Multipass logs) and `logs/` are gitignored output. With the CLI log on, every CLI call appends to `<Path>/cli-<yyyyMMdd>.log` (`CommandLog`; config section `CommandLog`: `Enabled` default false, `Path` default `%LOCALAPPDATA%\CoreBridge\logs` (taken from `SpecialFolder.LocalApplicationData`, so it works off Windows too), resolved like `MultipassLogPath`; `appsettings.Development.json` sets `Enabled: true` and `Path: artifacts/logs`, so a checkout logs into `artifacts/logs/`): arguments, output lines, prompts with their answers (free text only as a length), errors (plus their inner cause with stack trace, `ursache`) and exit code, one line each with timestamp and PID. Below that come the internals, which travel as events like Std/Err: `DiagnosticEvent` (a note: setup — environment, Multipass client/binary/recording, profile store, timeouts — and system changes: killing `multipassd`, `MULTIPASS_STORAGE` system variable, service registry value) and `ToolCallEvent : DiagnosticEvent` (one finished external call with tool, args, exit code, duration, stdout, stderr, note), created by `EventFactory.Diagnostic`/`ToolCall`; Core code on threadpool threads emits them with the synchronous `EventFactory.Post`. Sources: `TracingMultipassCli` (decorator around every Multipass client the CLI uses — the factory client in `Execute`, the `Doctor` check inside `MultipassService`, `MultipassAuthentication`; for doubles it reports their `BinaryLabel`; it is no `IMultipassDouble` itself, so check doubles with `cli.AsDouble()`), and an optional `EventFactory` parameter on `MultipassService` (`sc.exe`, kill), `GitCli`, `MultipassStorage` and `ElevatedRelaunch.RunAsync`. `ConsoleAdapter` ignores diagnostics; `CommandLog.Tee` writes them as `info`, or `aufruf` (command line) / `ergebn` (exit code, duration, timeout/kill) / `  out` / `  err` (each stream capped at 16 000 chars), and collapses identical consecutive calls (polling) into one plus a repeat count; the lifecycle fixture lets them pass to the log only. Secrets: `EventFactory.AddSecret` (the `multipass-store` passphrase) replaces them with `***` before an event enters the channel. A tool call's lines are written when it ends — an elevated window writes to the same file, so read it to see what happened there. Ticks are left out; a log that can't be opened is silently skipped. `mp-log/` and `experiment-data/` are checked-in recorded data, not source.

### CLI verbs (CommandLineParser)

Typical flow: `cb init-configure -n dev -c claude,dotnet` → `cb vm-create -n myvm --profile dev`.

- `multipass-status|restart` — restart first tries without elevation: whether the user may stop/start the service is decided by its ACL (`MultipassService.CanControlService`, `OpenService` with start/stop rights, no side effect), not by group membership. Only on access denied — up front, or mid-run (`MultipassAccessDeniedException`, e.g. killing the SYSTEM `multipassd`) — does it ask to relaunch itself elevated via UAC; the elevated window continues from the state it finds. The relaunch (`runas`, exit code back, `--pause-on-exit` keeping the admin window open) is `ElevatedRelaunch` in CoreBridge.Interaction, shared with `multipass-store`. The default Multipass ACL grants interactive users only query rights, so on a stock install the restart still elevates. If the stop hangs, it asks y/n before killing the service's `multipassd` PID. While it waits for the stop, `MultipassService.Restart` opens a `ChoiceEvent<HungStopOptions>` through its `offerWhileStopping` factory and the CLI carries it on its ticks: `k` kills `multipassd` right away without waiting for the timeout or asking y/n, `Esc` cancels (`OperationCanceledException`, exit 130), and Core closes it with the default "keep waiting" when the wait ends; if that kill needs elevation, the elevated window gets the hidden `--kill-now` and doesn't wait again. The waits for `Running` and for the daemon to answer `multipass version` (often longer than `DefaultTimeout` after a restart) ask "weiter warten?" after each `DefaultTimeout` instead of failing. Ticks keep coming while a single poll still blocks, so the spinner moves and keys are read. Prompts go through `EventFactory` interaction events, answered by `ConsoleAdapter` (default "no").
- `multipass-store [-p <path> | --reset] [-y]` — shows or changes where Multipass keeps its data (`MULTIPASS_STORAGE`; default `%ProgramData%\Multipass`). Logic in `Multipass/MultipassStorage.cs`. It writes the system variable (the documented way) **and** the service's own `Environment` value under `HKLM\…\Services\Multipass`, because the service control manager only passes a changed system variable on after a reboot; the service value wins when reading. VMs and images are not copied: they stay in the old folder, invisible. It carries over only `multipassd.conf` (`MultipassStorage.CopySettings`: daemon settings incl. `local.passphrase`), copied in the elevated window before the service restart and only where the target lacks it or has it empty; a fresh folder has it empty (recorded with 1.16.3). Trusted client certificates are not copied: `multipass authenticate` adds the client in the new folder, and the daemon creates its own certificates and SSH key itself. Asks first, offers to stop running VMs, elevates via UAC (relaunch with `--yes --pause-on-exit`) if needed, then restarts the service with `acceptRejectedClient` (a fresh folder doesn't know the client, so a rejecting daemon counts as up). The trusted client certificates live in the storage folder, and only an already trusted client may run `multipass set local.passphrase`. So before switching, the user's window sets a random passphrase (`MultipassAuthentication`, through its own unlogged `MultipassCli`, so the passphrase never lands in a `MultipassLogPath` log; it lives only in that run). After switching, it checks the client: `Doctor.Check` flags `NotAuthenticated` (`multipass version` still exits 0 then, just without `multipassd`; only `multipass list` says "not authenticated"). If rejected, it runs `multipass authenticate` with that passphrase and checks again. Still rejected means exit 1 with `Doctor.NotAuthenticatedMessage`: go back to the old folder, or repair/reinstall Multipass (the installing user is trusted automatically). Observed: the passphrase setting moves with `MULTIPASS_STORAGE` (a fresh folder answers "Passphrase is not set"), so the flow is: set passphrase → switch (with `CopySettings`) → `multipass authenticate`; without `CopySettings` the new folder answers "Passphrase is not set". Refused under `cb-sim`.
- `vm-list|create|start|stop|delete|exec|connect|put|get` — every VM verb first looks the VM up via `vm-list` and reports missing/trashed VMs with a ready message.
  - `vm-create` asks before replacing an existing VM of the same name (stop + `delete --purge`).
  - `vm-create --cpus N -m 4G -d 20G` → `multipass launch --cpus/--memory/--disk` (`VmResources`: validated up front, memory ≥ 128M, disk ≥ 512M). A profile may carry defaults (`init-configure --cpus/--memory/--disk`, optional `Cpus`/`Memory`/`Disk` in `<name>.profile.json`, still schema 4); a value given to vm-create beats the profile's.
  - With cloud-init, `vm-create` only reports success after the provisioning is proven: it waits in the guest for `cloud-init status --wait` and then requires the `/var/lib/corebridge/<c>.ready` marker of every profile component with a script (`InitInstall.Markers`). cloud-init's own status can't be trusted for that: its runcmd is a plain `sh` without `set -e`, so it reports success as long as the *last* script succeeds. A missing marker after cloud-init finished = that component failed: exit 1, the VM stays running, no snapshot. Without a profile (only `--cloud-init`) it only waits for cloud-init. This must happen before the snapshot: runcmd runs once per instance, so a snapshot of a half-provisioned VM never completes on a later boot.
  - `vm-start`/`vm-stop` are no-ops when the VM is already running/stopped. `vm-delete` asks before deleting a running VM. `vm-exec|connect|put|get` offer to start a stopped VM.
  - stop/delete ask "keep waiting?" after each `DefaultTimeout`, every start (vm-start, the start before exec/put/get/install, the restart after vm-resize) after each `DefaultTimeoutVmStart` (code default `3m`, issue #5; not in the signed appsettings). `vm-create` waits in `DefaultTimeoutVmCreation` slices and asks after each. On "no" the daemon keeps launching in the background, and a `TextEvent` reads a follow-up command that is parsed and dispatched like normal CLI args.
- `vm-clone|snapshot|snapshots|restore` — Multipass only clones/snapshots/restores **stopped** VMs, so a running one is stopped after asking.
  - `vm-clone` waits in `DefaultTimeoutVmCreation` slices because it copies the disk. On "no", Multipass finishes the clone in the background. The clone carries everything cloud-init installed in the source, so a provisioned base VM plus clones skips re-provisioning.
  - `vm-restore` always passes `--destructive` (without it Multipass prompts on a redirected stdout and hangs). It first takes a backup snapshot unless the user explicitly discards the current state, so without a console it always backs up.
- `vm-install -n <vm> -c dotnet,python [--snapshot <name>]` — installs components into an existing VM with the same steps cloud-init runs at create: wait for cloud-init, `apt-get update`/packages, snaps, upload the component script LF-normalized to `/tmp`, `install` it to its `InstallPath`, run it as `InstallUser`, then require its `/var/lib/corebridge/<c>.ready` marker. The plan is in `Inits/InitInstall.cs`. It starts a stopped VM without asking. The first failing step ends the command, names the step, and leaves the VM running for diagnosis.
- `vm-resize -n <vm> [-d 20G] [--cpus 2] [-m 4G]` — relays `multipass set local.<vm>.disk|cpus|memory=<value>` (`VmService.SetSetting`/`GetSetting`). Multipass only modifies **stopped** VMs and only grows disks, so shrinking and invalid values are rejected via `VmResources.Parse`/`MultipassSize` *before* a running VM gets stopped (after asking); values that already match are skipped. A VM that was running is started again, and cloud-init `growpart` grows the guest root partition on boot. The idea: keep base VMs/snapshots small and grow a clone when work starts.
- `repo-send -n <vm> [-r <path>]` / `repo-receive -n <vm> [-i <id>] [--diff] [--yes]` — task cycle, step 1: Claude's work in the VM goes back to the host repo. The names deliberately avoid git's own verbs (push/pull/fetch). Both verbs refuse under `cb-sim`. User walkthrough: `docs/task-cycle.md` (keep it in sync). Still to come: Stop hook `claude-checkpoint`, task lock/start, scanning.
  - No SSH: commits travel as `git bundle` files via `multipass transfer` + `multipass exec`, because `multipass exec` on Windows forwards no stdin, so git's live pack protocol can't run over it.
  - send: requires the git component (`git.ready` marker + git, fail closed). Uses the bare repo `~/repos/<repo>.git`. Bundles `main` with full history the first time and only `main ^<vm-main>` afterwards (fast-forward only, like a push without `--force`). Workspace `~/work/<repo>` is cloned, or only fetched (reset belongs to the future task start). The repo name comes from the common `.git`, so a worktree sends as its main repo.
  - receive: without `-i` it lists the `claude/*` branches of the bare repo. With `-i` it requires `main` checked out and clean, bundles `claude/<id>` in the VM (excluding the VM's `main` if the host has it), fetches it to `refs/remotes/<vm>/claude/<id>`, and shows log + diffstat. Only after yes/`--yes` does it fast-forward main (`merge --ff-only`; commit ids stay those from the VM). If main has commits the task branch lacks, nothing changes (exit 1): send main again and rebase the task in the VM.
  - `multipass transfer` VM→host exits 2 on Windows with "cannot set permissions for local file" although the file is complete. Only that exact message is tolerated.
- `init-configure|list|delete` — profiles (see `Inits/` below).
- `component-list [-n <c>]` / `component-add -n <c> --json|--yaml <file or text> [-f]` / `component-remove -n <c>` — manage the user's own components in `<StoreRoot>/appsettings.user.json` (`InitStore.UserSettingsFile`, logic in `Inits/InitComponentStore.cs`). Built-in components from `appsettings.json` can't be changed or removed, so an update of the installation never collides with user edits. `-n` on list prints a full definition as JSON (template for add). Add parses strictly (unknown keys fail), stores a relative `Script` as an absolute path resolved from the cwd, trial-renders cloud-init with only that component, and asks before replacing a user component (`--force` skips the question). Existing profiles keep their rendered cloud-init.
- `settings-verify [-f a,b]` — checks the OpenPGP signatures (`<file>.clearsigned.asc`, `<file>.asc`, or an in-place clearsigned file) of the shipped appsettings, or of the given files, against the embedded CoreBridge key and reports OK, UNSIGNIERT (warning, exit 0) or UNGÜLTIG with the reason per file (exit 3 if any signature is invalid). It is the only verb that starts when the config is badly signed (it loads the config with `SignaturePolicy.Ignore`).
- **Snapshot after configuration** is standard. After a successful `vm-install`, or a `vm-create` with profile/cloud-init, the CLI recommends a snapshot ("stable state before anyone connects") and asks yes/no (no console → no). With `--snapshot <name>` it takes one without asking. The VM is stopped for it and stays stopped. After a failure there is no offer.

## Architecture

- **CoreBridge.Core** — all logic; no console I/O. References CoreBridge.Interaction (never the other way round) so it can ask through the same `ChoiceEvent`s as CLI and TUI, e.g. the restart's `HungStopOptions` offer.
  - `Multipass/` (namespace `CoreBridge.Core.Multipass`): `IMultipassCli` is the seam; `MultipassCli` spawns `multipass.exe` and returns `MultipassRunResult` (exit code, stdout, stderr, duration); it is `virtual`/injectable for tests — `Run` waits once, `RunWithExtensions` waits in slices and asks a `keepWaiting` callback. `MultipassBinaryLocator` resolves the binary: env `CORE_BRIDGE_MULTIPASS_EXE` → `PATH` → `%ProgramFiles%\Multipass\bin\multipass.exe`. `MultipassService` backs `multipass-restart` (controls the Windows service via `sc` output parsing); its waits stream `Progress.ProgressTick` (`.`) lines, turned into `ProgressEvent`s, and throw `MultipassServiceTimeoutException`. Long VM verbs (create/start/stop/delete/clone/snapshot/restore/exec/put/get) run through `Program.WithProgress`, which emits a `ProgressEvent` every 200 ms while no interaction is open; `ConsoleAdapter` draws them as an in-place spinner `- / | \` with the seconds waited, or as dots when stdout is redirected (no carriage-return garbage in logs). When the user answers "keep waiting?" with no, create/clone report that Multipass continues in the background (exit 0); start/stop/delete say the same but exit 1, because a following step (delete after stop, exec after start) must not build on an unfinished state. `SimulatedMultipassCli` (free play-through) and `ReplayMultipassCli` (exact replay) are the stand-ins for development without Multipass (see below).
  - `Vm/`: `VmService` wraps the verbs. `Doctor.Check` backs `multipass-status`. `VmSession` is the abstract scripted-session base (`SendLine`/`WaitFor`) with `VmConsoleSession` (arbitrary process, test hook), `VmExecSession` (each command is its own `multipass exec … /bin/sh -c`, the reliable path on Windows; the working directory carries over between commands via a `pwd` marker line, env/shell variables don't) — all three live in `VmConsoleSession.cs`. `VmService.OpenConsole` is vm-connect in programmable form (used by the lifecycle connect stage); there is no SSH anywhere in CoreBridge.
  - `Inits/` (namespace `CoreBridge.Core.Inits`): `InitService.Configure` renders cloud-init from `Inits:Components` and writes `<name>.profile.json` + `cloud-init.yaml` into the `InitStore`. **It downloads nothing and manages no image** — a profile is purely generated cloud-init plus the Multipass catalog name to launch. `InitCloudInit` renders the cloud-init YAML from `Inits:Components` (packages, users, snaps, and component shell scripts from `scripts/components/*.sh` embedded as files and run **in the guest only** — the host never executes them; each script takes the install user as `$1`, checks its own postconditions and touches `/var/lib/corebridge/<component>.ready`; shipped: `claude`, `dotnet`, `python` (3.14 from the archive, else via uv), `cline` (npm, Node ≥ 20 via NodeSource if needed), `git` (only git; needed by `repo-send`/`repo-receive`, which run git inside the VM via exec — no sshd, no keys), plus snap-only `opencode`; `ComponentScriptTests` renders them from the real `appsettings.json`); `CloudInitYamlValidator` checks it. `InitProfileResolver` maps profiles to their runtime image (default `daily:26.10`) + cloud-init. `vm-create --profile <p>` uses `ResolveRequired` (a mistyped name lists the existing profiles instead of a catalog lookup; `--image` together with `--profile` is refused); `--image` is a catalog image, and for compatibility a profile name there still resolves (only if a profile file exists in the store), with a hint to use `--profile`. The output reads `Profil: dev → Image: daily:26.10`.
  - `Authenticity/` (namespace `CoreBridge.Core.Authenticity`): **verifying only, no signing in the product.** `PgpFileVerifier` (BouncyCastle.Cryptography) checks detached signatures `<file>.asc`: type CanonicalTextDocument (`gpg --textmode`, so a CRLF/LF switch by `core.autocrlf` doesn't break it; BinaryDocument is accepted too), a known, unrevoked and unexpired key, no MD5/SHA-1/RIPEMD-160. `TrustedKeys.CoreBridge` is the public key `corebridge-signing.pub.asc`, embedded as a resource (never from a config file) and pinned to fingerprint `7D67FF40…2A7F227B` (Ed25519, expires 2029-09-28 — after that every start fails until the key is extended, re-exported and re-embedded). `SettingsSignatures` decides what counts as signed and applies a `SignaturePolicy` (`Ignore`/`Optional`/`Warn`/`Required`): a file is signed if it is itself clearsigned (its cleartext is loaded), or has `<file>.clearsigned.asc` next to it (`gpg --clearsign`; the plain file is still what gets loaded, verified against that signature via `ClearsignedMessage.Canonicalize`, so an edit after signing is a mismatch), or a detached `<file>.asc`. `SignedFileProvider` plugs this into `ConfigurationBuilder` and collects `Warn` cases in `Warnings`. Signing is deployment: `scripts/sign-settings.ps1 -ClearSign` (Gpg4win; without `-ClearSign` it writes a detached `--detach-sign --armor --textmode` `.asc`; both then check VALIDSIG and `cb settings-verify`) or, without gpg-agent, `tools/CoreBridge.Signer` (`--key <secret.asc>`, passphrase from `CORE_BRIDGE_SIGNING_PASSWORD` or a prompt). The Signer is referenced only by the tests.
  - `Git/` (namespace `CoreBridge.Core.Git`): `GitCli` runs git on the host (`virtual`, `GitException` for start failures/timeouts, translated in `Program.ToExecutionException`), `SandboxRepo` holds the pure pieces (VM paths, bundle paths, id rules, VM shell lines, ref parsing). `Common/Shell.Quote` is the shared quoting for guest shell lines.
  - `InitStore` is static state: `Initialize(StoreRoot)` once at startup. **Path resolution lives in `Common/RepoPaths.cs`** — `Root()` finds the directory holding `CoreBridge.slnx` by walking up from the DLL, `Resolve()` anchors relative paths there. That is the *only* place a configured path gets resolved; `Inits:StoreRoot` is the relative `artifacts` in the Development default, so a private copy of this logic per caller makes files land in different places depending on the working directory. Default is `<repo>/artifacts` (gitignored). Layout: `profiles/<name>/<name>.profile.json|cloud-init.yaml`. `SchemaVersion` is 4 and the resolver rejects anything below 4 (profiles from the pre-4 model era must be re-created) — treat a bump as breaking for existing profiles.
  - **Logging & replay (no env vars)** — `CoreBridgeContainer.Create(config)` (`Common/`) builds an MS DI container (`Microsoft.Extensions.DependencyInjection`, `ValidateOnBuild`) from `AppConfig.Bootstrap` (interface FullName → implementation FullName, default `IMultipassCli → MultipassCli`; `AppConfig` is registered as an instance, so implementations may take it in their ctor; MS DI picks the ctor with the most resolvable parameters, so give an implementation exactly one public ctor — `ReplayMultipassCli.FromEntries` exists for that reason). `MultipassCliFactory.Create(services)` resolves `IMultipassCli` and, if `MultipassLogPath` is set, wraps it in `LoggingMultipassCli`, which writes each call (args, exit code, stdout/stderr, `timedOut`) as JSON Lines to `<MultipassLogPath>/<yyyyMMdd-HHmmss>-<pid>.jsonl` (resolved via `RepoPaths`). Mapping `IMultipassCli` to `ReplayMultipassCli` replays those logs instead of calling Multipass: exact args match, identical calls answered in recorded order (the last one repeats), an unrecorded call throws `MultipassException`, a recorded timeout rethrows; it is never wrapped in logging and does not call `keepWaiting`. It reproduces no host side effects (e.g. the local file from `transfer`) and installs nothing in a guest; use it for exact regression replays, not for exploring.
  - **Simulation** — `SimulatedMultipassCli` lives in the test-side library `test/CoreBridge.Simulation` (namespace `CoreBridge.Simulation`), not in Core; `CoreBridge.Cli` references it **only in Debug** so `cb-sim` can load it via the assembly-qualified `Bootstrap` entry in `src/CoreBridge.Cli/appsettings.Simulation.json` (`"CoreBridge.Simulation.SimulatedMultipassCli, CoreBridge.Simulation"`); a Release build has no simulator. It keeps VMs, snapshots and transferred files as state in `<StoreRoot>/multipass-sim/state.json` (cross-process mutex; reset by deleting the folder) and accepts any names/orders. Long verbs (launch/start/stop/restart/clone) take `MultipassSimulationDelay` (default `4s`) in slices like `MultipassCli`, so "keep waiting?" and background completion (state already changed, like the real daemon) can be played through with a small `-t`. `exec` runs through `SimShell`, a small POSIX-sh subset over a virtual guest filesystem (transferred/redirected files, `mkdir` directories, `.ready` markers, installed component binaries, `/etc/os-release`): quoting, `$VAR`/`${VAR:-x}`/`$?`, `$(…)`, `$((…))`, `;`/newline/`&&`/`||`/`|`/`!`, redirections, `cd`/`pwd`, `test`, `printf`, `.`, `exit`, `sudo` (→ root), `command -v`, `cat`/`ls`/`grep`/`head`/`install`… — enough for `VmExecSession`'s cwd-marker scripts. No `if`/`for`/functions; an unknown command without a path succeeds silently so free play-through isn't blocked by `apt-get` & co. Relative transfer paths land under `/home/ubuntu`. Cloud-init is assumed successful: components found in the launch cloud-init (`corebridge-install-<name>`) answer their probes (`--version`, `.ready` markers) and travel with clones/snapshots. Output, error texts, clone/snapshot naming (`<src>-cloneN` counting named clones too, `snapshotN`, parent = last taken/restored) and list order (active VMs alphabetically, then trash) follow real recordings in `test/CoreBridge.Core.Tests/Recordings/multipass-1.16.3/`; `SimulatedMultipassCliTests.SimulatorEntsprichtDerEchtenAufnahme` replays them against the simulator. Re-record with `MultipassLogPath` pointing there when Multipass changes. `list`/`list --snapshots`/`info` answer as table by default (like Multipass) and with `--format json|csv`. **`multipass-sim.exe`** (`tools/CoreBridge.MultipassSim`, logic in `MultipassSimCommandLine`) is the same simulator as a standalone binary with `multipass.exe`'s command line, plus an interactive `shell` (starts a stopped VM, cwd carries over). State defaults to `<repo>/artifacts/multipass-sim/state.json` (the same as `cb-sim`); env `CORE_BRIDGE_SIM_STATE` / `CORE_BRIDGE_SIM_DELAY` (default `4s`) override. A hidden `multipass-sim sync [--markers] [--exe <multipass.exe>]` (not in its help, since multipass has no such verb; `SimulatedMultipassCli.SyncFrom`) replaces the simulated inventory with the real one: VMs (name, state, IPv4 as reported incl. `N/A`, release, disk/cpus/memory via `get`) and snapshots (parent, comment), with name counters set so `snapshotN`/`-cloneN` continue the real numbering. It only reads from real Multipass (`list`, `list --snapshots`, `get`; `--markers` adds `ls /var/lib/corebridge` via exec in running VMs). Guest content `list` can't show (components, markers, files) is kept for VMs the simulator already knew; simulated VMs that don't exist for real are dropped. It never resolves to itself when `CORE_BRIDGE_MULTIPASS_EXE` points at `multipass-sim.exe`. `SimulatedBinaryMultipassCli` is the real `MultipassCli` pointed at that exe (state/delay from the config, passed to the child via the `MultipassCli.PrepareProcess` hook), so the process path is exercised without VMs; it is an `IMultipassDouble` too. Plain `cb` with `CORE_BRIDGE_MULTIPASS_EXE=<…\multipass-sim.exe>` also works, but then nothing knows it is a double: no notice, logging on, and `multipass-store` would still change the real service. The doubles (Replay, both simulators) implement `IMultipassDouble`: never logged, `multipass-status` shows their pseudo path, and every VM command starts with a `[simulation://multipass] kein echtes Multipass` stderr notice. Logging is off by default; to mock locally put `"MultipassLogPath": "artifacts/mp-log", "Bootstrap": { "CoreBridge.Core.Multipass.IMultipassCli": "CoreBridge.Core.Multipass.ReplayMultipassCli" }` in `appsettings.local.json`. `multipass-restart` always stays real.
- **CoreBridge.Interaction** — the UI-neutral event/prompt layer shared by Core, CLI and TUI, with no dependency on Core: `CliEvent`/`InteractionEvent`/`ChoiceEvent<T>`, `OptionDef` (option metadata incl. `Keys` and `IsDefault`), `EventFactory`, `ConsoleAdapter`, `ElevatedRelaunch` (UAC relaunch) and `ProgramExecutionException`. Its behaviour is described under "CLI event stream" below; `tools/CoreBridge.Interaction.Demo` exercises it in a real console.
- **CoreBridge.Cli** — `Program.RegisteredOptionTypes` is the single list of verbs; `Program.Run(config, options, ct)` is the one public dispatcher (internally `Dispatch(CommandContext, IOptions)`, where `CommandContext` bundles config, `VmService`, `EventFactory` and token) and returns `IAsyncEnumerable<CliEvent>` streamed as they are produced. Every expected failure leaves `Program.Run` as a single `ProgramExecutionException` whose message is ready to display and which carries the exit code: `Program.ToExecutionException` is the one place that translates `MultipassException`, JSON and I/O exceptions and cancellation (Ctrl+C → 130). `Main` only prints it; anything else is a bug and propagates. To add a verb: add an `[Verb]` options class implementing `IOptions` in `Options.cs`, register it in `RegisteredOptionTypes`, and add a case to `Dispatch`.
  - **Menu from the attributes** — `CommandMenu.cs` exposes the verbs as data: `CommandMenu(Name, Help, IReadOnlyList<CommandParameter>)` with `CommandParameter(Name, Abbreviation, Required, Help)`, accessed via `CommandMenus.All` (same order as `RegisteredOptionTypes`), `CommandMenus.ByName` (OrdinalIgnoreCase), `CommandMenus.Find(name)` and `CommandMenus.For<VmCreateOptions>()` / `For(Type)`. **The attributes in `Options.cs` are the only source**: name, help, short form and `Required` are stated exactly once, on the `[Verb]`/`[Option]` attribute; there is deliberately no second, hand-maintained list. They are read via reflection over `Program.RegisteredOptionTypes`, once on first access and then cached in a `Lazy` (no runtime cost). `GetProperties` includes inherited properties, so `-t/--timeout` from `MultipassOptions` shows up automatically, and `Hidden` options (`pause-on-exit`) are filtered out via `{ Hidden: false }`. `CommandMenuTests` checks the result against the real CommandLineParser: every menu entry parses with exactly its required options, and the parser reports missing required options the same way the menu marks them. A Roslyn source generator was deliberately rejected — ~300 lines of code to produce a list that reflection delivers in 40.
- **CLI event stream** — `Program.Run` creates a `Channel<CliEvent>`, starts the command task (`ProduceAsync`) and returns `channel.Reader.ReadAllAsync()`. `EventFactory` (a field of `CommandContext`, one instance per call with its own `Stopwatch`) creates every event and timestamps it: `Std`/`Err`/`Tick`, plus `Choice<T>`/`Text`, which record open prompts in an `IOpenInteraction` set. `ConsoleAdapter` is the consumer: it writes Std/Err/Tick and answers prompts through the non-generic `IChoiceInteraction` (any `ChoiceEvent<T>`, without knowing the enum). Order in its `switch` matters, because `InteractionEvent` derives from `StdEvent`. A `ProgressEvent` may carry an `Offer` (`EventFactory.Tick(offer)`): an `IChoiceInteraction` created with `Choice<T>` (so it is tracked like any prompt) that stays open while the work goes on, so the user can skip or cancel. It travels only on ticks, never as an event of its own: `ConsoleAdapter` shows the options that have `OptionDef.Keys` next to the spinner, reads `Console.KeyAvailable` on each tick and answers via `IChoiceInteraction.TryChooseKey`; consumers that skip ticks (the lifecycle fixture, no console) never see it. The producer closes it with its default when the wait ends, so `AssertNoOpenInteractions` still holds. Prompts come from `context.ConfirmAsync`/`PromptAsync` (awaiting) or `EventFactory.Ask` (**blocking**). `Ask` exists for the `Func<bool>` callbacks from Core, which run on threadpool threads and can't `await`; that is why the stream is a channel and not a plain async iterator. Without interactive input, the value marked `[OptionDef(..., IsDefault = true)]` always wins (`No`/`Cancel`, `null` for free text), **not** `default(T)`, because the first enum value is the affirmative one here. Exactly one value per enum must be marked, otherwise creating the prompt throws. The check is `ConsoleAvailability.CanPrompt`, on top of `Console.IsInputRedirected`, because `ReadLine` without a console window blocks forever. At the end, `ProduceAsync` calls `AssertNoOpenInteractions`: a prompt that was never answered is an error, not a hang.
- **Config** (`AppConfig`, shared by CLI and TUI): `Main` checks `appsettings.json` and, if it exists, `appsettings.{env}.json` next to the CLI (`SignaturePolicy.Warn`): a missing signature prints a warning to stderr (and the CLI log) and continues; a present but invalid one — unknown key, broken, or the file changed after signing — stops with exit 3 (`SettingsSignatureException`) in every environment, so **every edit of a signed file needs `.\scripts\sign-settings.ps1 -ClearSign`**. The shipped files and their `.clearsigned.asc` are committed and always copied to the output, for every developer: they are not meant to be edited without the key — local overrides go into `appsettings.local.json`, components into `appsettings.user.json` (`component-add`). `appsettings.local.json` and `appsettings.user.json` may be unsigned without a warning, but are verified once signed (`SignaturePolicy.Optional`); `component-add`/`-remove` refuse to rewrite a signed `appsettings.user.json`. Env vars are not checked. `Program.Run` receives a finished config, so the lifecycle tests are not affected. Load order: `appsettings.json` → `appsettings.{DOTNET_ENVIRONMENT}.json` (defaults to `Development`, which sets `StoreRoot=artifacts`) → `appsettings.local.json` (gitignored) → env vars (`Inits__StoreRoot`). Timeouts are top-level strings `DefaultTimeout` (restart / `sc`, vm-list/stop/delete/exec/put/get; code default and appsettings `30s`), `DefaultTimeoutVmStart` (every VM start, code default `3m`) and `DefaultTimeoutVmCreation`, parsed by `StringExtensions.ReadTime` (`5m`, `10s`, `1000ms` only). Verbs deriving from `MultipassOptions` (`Options.cs`) take `-t/--timeout`, whose getter is private: only `Program.ApplyTimeoutOverride` (called from `Run` and for vm-create's follow-up command) reads it via `ITimeoutOverride` and replaces all three config values for that call. Everything else reads only the config. `MultipassLogPath` (off when empty) and `Bootstrap` choose logging/replay (see above). `CommandLog:Enabled`/`CommandLog:Path` control the CLI log (`CommandLogConfig.ResolveDirectory`); an elevated window reads the same appsettings files but not the caller's env vars, because UAC passes only arguments. User components are not a config layer: `Program.Run` adds only `Inits:Components` from `<StoreRoot>/appsettings.user.json` via `InitComponentStore.Merge` after `InitStore.Initialize`, so the file can't change StoreRoot. The location follows the environment (installation `%LOCALAPPDATA%\CoreBridge`, Development/Simulation `<repo>/artifacts`), never the project folder. A name that is also built in is an error, not a merge. No secrets in config; passwords come only from the `CORE_BRIDGE_[ALL|<NAME>]_PASSWORD` env chain.
- **CoreBridge.Tui** — Terminal.Gui **v2** app, not yet wired to Core. Before touching UI code, read `src/CoreBridge.Tui/AGENTS.md`: v2 is a full rewrite and v1-style code won't compile. `src/CoreBridge.Tui/CLAUDE.md` points there too. `Program.cs` uses the instance lifecycle `Application.Create().Run<MainWindow>().Dispose()`. `MainWindow` (`MainWindow.tui.cs`, a `Runnable`) nests the project's own `Controls/Splitter`, a collapsible two-pane split with a fixed-size pane. The csproj picks up `*.tui.xaml` as `AdditionalFiles`. The root `Ui-Reference-*.md` files are ASCII mockups of the target layout: a log pane and a preview pane that collapse into each other through "Show Log / Show Preview" bars.

## Tests

- **CoreBridge.Core.Tests** — xUnit unit tests; Multipass calls are faked via `MultipassCli` subclasses / locator parameters.
- **CoreBridge.Cli.Tests** — one ordered lifecycle, written once in the abstract `CliLifecycleStages` and run three times: `CliLifecycleTests` against real Multipass (`[Trait("Category","Integration")]`, details below), `CliLifecycleSimulationTests` against the in-process `SimulatedMultipassCli` (store `artifacts/cli-lifecycle-sim/store`, ~1 s) and `CliLifecycleSimulatedBinaryTests` through the real `MultipassCli` against `multipass-sim.exe` (`SimulatedBinaryMultipassCli`, store `artifacts/cli-lifecycle-simexe/store`, ~6 s; the test project references the exe project with `ReferenceOutputAssembly="false"` so it gets built). The simulated variants have no trait, so they are part of the fast run; they use `MultipassSimulationDelay` 100ms and skip the daemon restart in Stage00. All share one collection because `Program.Run` sets the static `InitStore`. Anything outside `Program.Run` (vm-connect) must take its client from `fixture.Cli`, never `new VmService()`, or the simulated run hits real Multipass. Real lifecycle: methods are named `Stage00_…`, `Stage01_…`, `Stage05b_…` and sorted ordinally by `LifecycleTestCaseOrderer`; each stage builds on the state the previous one left. Stages don't re-check what earlier stages did. They can also be run one at a time in order, each in its own run: `CliLifecycleFixture` uses fixed per-checkout names (`cbx-cli-vm-<checkout folder>`) and the persistent store `<repo>/artifacts/cli-lifecycle/store`, and cleanup happens only in Stage08 (vm-delete) / Stage09 (init-delete), not on dispose. Stage00 levels the field depending on what it finds: an unresponsive daemon is restarted; a test VM in a transitional state (`Unknown`, `Starting` …) usually has the daemon stuck on it, so the daemon is restarted first and the state re-read; a leftover test VM is stopped, purged and the daemon always restarted afterwards (otherwise it can keep tasks for the deleted VM, e.g. its startup "Waiting for SSH", and hit the new VM of the same name with them — observed: `Save-VM` mid-launch although the old VM was Stopped when deleted; the VM's state doesn't reveal whether the daemon holds such a task); finally `multipass-status` must report a healthy daemon. Without admin rights the restart goes through UAC into an admin window that waits for a key at the end. Prompts have no default answer: each `RunAsync` call scripts its dialog in order as `Cli.Asks("<part of the prompt>").TestInputs("<console input>")`, the input is parsed like typed console input, and any deviation (extra or different prompt, invalid input, a scripted prompt never asked) cancels the prompt, ends the command and fails `AssertSucceeded` — a blanket yes would answer "keep waiting?" on a hung launch forever. It calls `Program.Run` in-process (no child CLI process), records every real Multipass call to `artifacts/mp-log/cli-lifecycle/` via `MultipassLogPath`, writes each command to the CLI log like `cb` does (`CommandLog.Tee` around `Program.Run`; `Enabled`/`Path` read from `src/CoreBridge.Cli/appsettings.Development.json`, so test runs land in `artifacts/logs/cli-<date>.log`, end lines marked `(Test)`) (Bootstrap stays default, so it is always real Multipass), creates a real profile + VM named `cbx-cli-*`, and skips itself when Multipass is unavailable.
- VMs created by tests use the `cbx-` prefix; `scripts/group-vms.ps1` groups them into a Hyper-V VM group (`-Remove` to undo).
